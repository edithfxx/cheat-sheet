## 決策 1：Vue 3 CDN，而非 Vite / TypeScript 專案

**選項**
- A. Vue 3 CDN global build，零建置
- B. Vite + Vue SFC + TypeScript
- C. 純原生 JS，無框架

**選擇：A**

這是個人速查表，使用情境是「寫 code 卡住 → 3 秒內找到並複製」。這個情境要求工具**隨時能開**。選 B 的話，每次換電腦都要 `npm install`、每次改一行都要等 dev server 起來，違背了工具本身的目的。選 C 則要自己處理列表渲染與狀態同步，5 種卡片型別的條件渲染會寫得很痛苦。

**代價（明確承擔）**
- 不能用 SFC、`<script setup>`、`defineComponent`
- 無型別檢查、無 tree-shaking、無編譯期錯誤
- `script/app.js` 只能是單一大檔（710 行），無法拆成元件檔
- `<script>` 載入順序被綁死：`vue.global.prod.js` → `config.js` → `app.js`，且不能改成 `type="module"`
- 依賴 unpkg CDN，離線環境無法使用

> 若這個專案要變成多人協作或需要長期維護，這個決策應該被推翻。它成立的前提是「單人、單機、工具型」。

## 決策 2：5 種卡片型別，不再增減

**選項**
- A. 只做 `code` 一種，所有內容都當程式碼存
- B. 5 種型別（`code` / `lines` / `table` / `sections` / `note`）
- C. 更細的分型（再拆出「指令+說明」「圖片」等）

**選擇：B**

型別不是為了分類好看，而是**每種型別對應一種不同的複製行為**：

| 型別 | 複製行為 | 若併入 `code` 會怎樣 |
|---|---|---|
| `lines` | 每行獨立複製 | 終端機指令得手動反白，失去價值 |
| `table` | 逐列複製 `key` | 對照表變成一坨純文字 |
| `sections` | 逐區塊複製 | 多解法無法摺疊，卡片變超高 |
| `note` | **無複製按鈕** | 觀念筆記出現無意義的複製鈕 |

**代價**
- `content` 成為多型欄位，新增型別時要同步改 `setEditType()`、渲染模板、`getFullContent()`、搜尋比對 `matchKeyword()` 四處
- 匯入驗證無法簡單檢查 `content` 形狀（見 [`DATA_SCHEMA.md`](DATA_SCHEMA.md) §4）
- 編輯既有卡片時**型別鎖死不可改**，因為改型別等於整個 `content` 要重填

## 決策 3：localStorage 為資料權威，JSON 檔只是種子

**選項**
- A. JSON 檔為權威，每次變更都要手動改檔案
- B. localStorage 為權威，JSON 只在首次載入時當種子
- C. 接後端資料庫

**選擇：B**

C 直接排除——不做後端是專案前提。A 與 B 的差別在於「編輯後要不要手動存檔」。選 B 之後，任何新增／編輯／刪除都由 `watch(allCards, ...)` 自動寫回 localStorage，使用者永遠不需要找儲存按鈕。

**代價（這是全專案最大的取捨）**
- **清除瀏覽器快取 = 資料全失**。這個風險必須靠使用者養成匯出習慣來補，而不是靠程式
- 換電腦、換瀏覽器都不會自動同步
- localStorage 上限約 5MB（估算可存 1000+ 張卡），超過時只能在 `saveToStorage()` 內 toast 提示
- 為了彌補，額外做了匯出／匯入／重置三個功能，等於把「同步」的責任交給使用者手動執行

## 決策 4：卡片預覽前 N 行 + 點擊開 Modal，而非原地展開

**選項**
- A. 原地展開（accordion）
- B. 點擊開 Modal 看完整內容
- C. 全部完整顯示，不截斷

**選擇：B**

桌面是 4 欄 grid 版面。選 A 會導致展開時把整列卡片撐高，其他卡片位置全部跳動；選 C 則讓一張 60 行的 Vue 初始架構卡把整個版面撐爛。Modal 讓卡片高度維持整齊，且能用 `Esc` 快速關閉，符合「查完就走」的使用節奏。

**代價**
- 多一層 Modal 狀態要管理（`activeCard`），且與其他 Modal（設定、編輯、刪除確認、子分類）的 `Esc` 關閉順序需要明確定義，見 `script/app.js:140`
- 無法同時比較兩張卡片的內容
- Modal 目前沒有 focus trap（見文末 Open Issues）

## 決策 5：單一資料檔 `data/update/data.json`，且無 fallback

**選項**
- A. 掃描 `data/` 資料夾，載入所有 JSON
- B. 多來源優先序：`update/` 找不到就退回 `default/` 種子資料
- C. 單一固定檔名，找不到就報錯

**選擇：C**

A **在技術上不可行**——瀏覽器的 `fetch()` 無法列出目錄內容，前端拿不到檔案清單。這是純前端架構的硬限制，不是偏好問題。

原本採用 B，`data/default/` 存放種子資料。2026-05-28 移除，理由是：兩個資料來源會讓「我現在看到的是哪一份」變得難以判斷，尤其在 localStorage 也參與優先序的情況下，變成三層來源，出錯時很難 debug。收斂成單一來源後，載入邏輯只剩三行判斷（`script/app.js:74`）。

**代價**
- 找不到 `data.json` 時**直接顯示錯誤，沒有任何 fallback**，首次使用者會看到空畫面加錯誤訊息
- 檔名被寫死，使用者匯出後**必須手動改名成 `data.json`** 才能生效——這是明顯的 UX 摩擦，但在無後端前提下沒有更好的解

## 決策 6：匯入衝突提供三種策略，而非直接覆蓋

**選項**
- A. 直接覆蓋同 id 卡片
- B. 直接略過同 id 卡片
- C. 讓使用者選：覆蓋 / 略過 / 另存為新卡

**選擇：C**

這是全專案最細緻的一段邏輯，因為三種情境都真實存在：

- **覆蓋**：在 B 電腦改過的卡片，要同步回 A 電腦 → 匯入版本較新
- **略過**：只想補進新卡，不想動本機已改過的內容 → 本機版本較新
- **另存為新卡**：兩邊都改過同一張卡，都想保留 → 重新產生 UUID，標題加註「(匯入)」

只做 A 或 B 都會在另外兩種情境造成**無聲的資料遺失**。而資料遺失在這個專案特別嚴重，因為決策 3 已經讓 localStorage 成為唯一權威，沒有備份可救。

實作上先用 `id` 分出 `duplicates` 與 `newOnes`（`script/app.js:457`），**無衝突時完全不打擾使用者**直接匯入；有衝突才跳出選擇 Modal。完成後產出 `{ added, overwritten, skipped }` 三段式報告，讓使用者確認結果符合預期。

**代價**
- 匯入流程從 1 步變成 3 步（選檔 → 選策略 → 看報告）
- 需要 `pendingImport` 暫存狀態，以及取消時的清理邏輯（`cancelImport()`，`script/app.js:477`）
- `asNew` 策略會產生標題重複的卡片（僅差「(匯入)」後綴），使用者需自行整理

## 決策 7：UUID v4 當 id，而非流水號

**選項**
- A. 遞增流水號
- B. UUID v4
- C. 用 `title` 當唯一鍵

**選擇：B**

直接由決策 6 推導而來。若用流水號，兩台電腦各自新增卡片都會產生 `#12`，匯入時無法判斷「這是同一張卡的兩個版本」還是「兩張不同的卡」——衝突偵測會全面失效。C 則會讓改標題等同於換一張卡。

**代價**
- id 不可讀，手動編輯 JSON 時難以辨識
- 自行以 `Math.random()` 實作（`script/app.js:643`）而非 `crypto.randomUUID()`，亂數品質較低。對單人工具的碰撞機率而言可接受，但若要嚴謹應改用 `crypto.randomUUID()`

## 決策 8：主分類順序固定，且新增分類需改程式碼

**選項**
- A. 分類由資料動態推導
- B. 分類寫死在 `script/config.js` 的 `CATEGORIES`

**選擇：B**

分類順序帶有語意——由基礎到框架的學習路徑排列。若由資料推導，順序會隨卡片增減而變動，使用者的肌肉記憶（「CSS 在左邊數來第三個」）就失效了。

子分類則相反，**採動態推導**（`subcategories`，`script/app.js:242`）：子分類數量多、變動頻繁，寫死會造成維護負擔。

**代價**
- 新增主分類必須改 `script/config.js`，非技術使用者做不到
- `CATEGORIES` 與資料脫鉤：卡片的 `category` 若不在清單中，該卡**不會出現在任何分類頁**，且沒有任何警告
- 分類是否合用只能靠人工回頭檢視。目前 8 個分類共 80 張卡，分佈不均（CSS 26 張、Vue3 僅 4 張），但因順序帶有語意，不會依數量重排

## 決策 9：移除語法高亮（2026-05-28）

**選項**
- A. 修正既有的 regex 高亮
- B. 改用 Prism.js / highlight.js
- C. 整個移除，一律顯示跳脫後的純文字

**選擇：C**

原本以 regex 自製語法高亮，遇到含 `<`、`"`、`/* */` 的內容（SQL、IIS 設定、Linux 指令等雜語法）會插壞 HTML 結構，導致畫面錯亂。A 需要對每種語言寫規則，投入與收益不成比例；B 會引入額外 CDN 依賴，違背決策 1 的輕量前提。

速查表的核心價值是**準確複製**，不是好看。顯示錯誤比沒有顏色嚴重得多。

**代價**
- 程式碼一律無色，可讀性下降
- `language` 欄位保留但降級為純 metadata，不影響任何顯示邏輯——這是刻意保留的擴充點
- 搜尋關鍵字高亮（`highlightText()` + `mark.hl-search`）不受影響，仍正常運作
